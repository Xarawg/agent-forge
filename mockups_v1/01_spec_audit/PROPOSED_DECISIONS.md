## Q-01. Данных API не хватает для «прогон ждёт accept» — read-only расширение API

- **Severity:** blocker · **Impact:** UX, dev
- **Находка:** приоритет №1 (видимость гейта на канбане) невозможен на чистом
  клиенте. `/api/run/<run_id>` не отдаёт: (а) полную очередь из tasks.yaml в
  топологическом порядке, (б) список `accepted` из run.json. Логика детекции
  — `forge/report.py::_gate_wait` (строки 100–116): прогон стоит, если первая
  недовершённая задача в topo_order идёт после done-задачи с `gate`, которой
  нет в `accepted`. Спека §1.1.7 прямо фиксирует отсутствие подсказки.
- **Предлагаемое решение:** расширить `GET /api/run/<run_id>` read-only
  полями (сервер по-прежнему ничего не пишет в `runs/`):
  - `queue`: вся очередь из `meta.tasks_path` в топологическом порядке —
    переиспользовать `report.build_report` / `_load_package`;
  - `gate_wait`: `{"task_id": <id>} | null` — серверная детекция, один
    источник истины с CLI;
  - `accepted`: список принятых задач (для бейджа «принято» на карточке).
  В UI: sticky-баннер над канбаном «⏸ Прогон ждёт решения» + команда
  `forge accept <id> && forge resume <run>` с кнопкой копирования; гейт-задача
  на канбане получает бейдж «ждёт accept» и визуальное выделение.
- **Правки спеки:** §2.1 (таблица API — новые поля `GET /api/run/<run_id>`);
  §2.3 строка «Подсказка ожидания гейта»: UI — «Есть (баннер + бейдж)»;
  §3 п.1 — закрыт; §1.1.7 — переписать сценарий.
- **Альтернатива:** клиент сам запрашивает очередь отдельной ручкой и считает
  gate-wait на JS — дублирует логику CLI, риск расхождения вердиктов UI/CLI.

## Q-02. Честный «N из M»: queued-задачи без журнала

- **Severity:** blocker · **Impact:** UX, dev
- **Находка:** §2.1: `/api/run/<run_id>` включает только задачи с
  journal-записями; §2.3 и §3 п.5 фиксируют, что полная очередь и «N из M»
  видны только в CLI. Для владельца, смотрящего только в браузер, прогресс
  систематически завышен.
- **Предлагаемое решение:** то же расширение `queue` из Q-01. В UI:
  - прогресс-бар в шапке: «Сделано N из M» + процент (N = done, M = вся
    очередь; failed/blocked считаются отдельно и подписаны);
  - queued-задачи без журнала рендерятся в колонке «Очередь» «призрачными»
    карточками: title/id/gate из tasks.yaml, без $/токенов, пометка
    «ещё не запускалась», пониженная контрастность, без клика (журнала нет).
- **Правки спеки:** §2.1 (ограничение «только задачи с journal-записями»
  снято для `queue`; массив `tasks` остаётся как есть для совместимости);
  §2.3 строка «Таблица задач прогона» — паритет достигнут; §3 п.5 — закрыт.
- **Альтернатива:** показывать «N из M» только по задачам с журналом —
  нечестный прогресс, противоречит философии «честные остановки».

## Q-03. Визуальная система: токены site/ поверх инструментальной плотности

- **Severity:** major · **Impact:** UI
- **Находка:** директива — тёмная тема в духе `site/`. Но `site/` —
  маркетинговый лендинг (крупная типографика, film-grain, анимации), а UI
  прогонов — плотный инструмент (7 колонок, mono-данные, polling 3 с).
  Прямое копирование приёмов лендинга ухудшит читаемость.
- **Предлагаемое решение:** взять **токены**, а не декор лендинга:
  `--bg #0a0a0a`, `--bg-raised #111`, `--surface #1a1a1a`, `--border #2a2a2a`,
  `--text #f0f0f0`, `--text-dim #888`, `--accent #d40027`,
  `--success #2ea043`, `--warning #d29922`, `--danger #f85149`,
  radius 3px, mono-шрифт для id/команд/чисел, section-label с линией.
  Состояния: done→success, failed→danger, blocked/validating→warning,
  running→`#79c0ff` (голубой из code-палитры site), review→`#bc8cff`,
  queued→`#888`. Акцент `#d40027` — только для действий и гейт-сигналов
  (баннер «ждёт accept»), чтобы не размывать. Film-grain и hero-анимации —
  **не переносим** (шум поверх данных, мерцание при polling).
- **Правки спеки:** §4 новый пункт «Визуальная система — токены site/…».
- **Альтернатива:** оставить GitHub-dark палитру текущего UI — отклонено
  директивой владельца.

## Q-04. Язык интерфейса: RU по умолчанию + переключатель EN

- **Severity:** major · **Impact:** UX, UI
- **Находка:** противоречие — §4.7 «интерфейс — русский», директива владельца
  — переключатель рус/англ. Директива новее спеки.
- **Предлагаемое решение:** паттерн `site/`: словарь `I18N = {ru:…, en:…}`,
  `data-i18n` атрибуты, кнопка RU/EN в шапке, выбор в `localStorage`.
  **Дефолт — русский** (§4.7 как первичная аудитория). Переводятся только
  строки хрома (колонки, кнопки, баннеры, пустые состояния); контент задач
  (title, note, команды) — как есть в данных.
- **Правки спеки:** §4.7 → «интерфейс — русский по умолчанию, переключатель
  EN; выбор сохраняется локально»; §3 п.12 — закрыт.
- **Альтернатива:** автоопределение по `navigator.language` — недетерминиро-
  ванный первый экран; отклонено.

## Q-05. Объём итерации v1: что берём из 14 пробелов

- **Severity:** major · **Impact:** UX, dev
- **Находка:** §3 перечисляет 14 пробелов; владелец зафиксировал 4 приоритета.
  Часть остальных — бесплатные попутно, часть требует новых мутаций/графиков.
- **Предлагаемое решение (пакет P0):**
  - **Берём:** п.1 (Q-01), п.5 (Q-02), стоимость наглядно (итог в шапке +
    прогресс-бар «потрачено / сумма капов» во вкладке Отчёт), п.14 частично
    (Q-07), п.6 «простым языком» (данные те же, что для Q-01/Q-02 — блок
    «Получилось / Не получилось / Ждёт решения / Что дальше» в Отчёте),
    п.7 частично (per-run кап с вердиктом + модели по ролям + версия
    промптов — всё уже есть в run.json, чистый рендер).
  - **Не берём (v2+):** п.2 (запуск из UI — мутация, отдельное одобрение),
    п.3 (diff ветки), п.4 (график стоимости по времени), п.8 (dry-run),
    п.9 (события всего прогона / поиск), п.10 (wizard: add/remove/depends_on),
    п.11 (звук/бейдж), п.13 (таблица прогонов).
- **Правки спеки:** §3 — пометить п.1, 5, 6, 7(част.), 12, 14(част.) как
  закрытые в v1; остальные — «отложено v2».
- **Альтернатива:** только 4 приоритета, без п.6/п.7 — отчёт останется
  беднее CLI при нулевой дополнительной стоимости данных.

## Q-06. Действия из UI: только копирование команд, без accept-кнопок

- **Severity:** major · **Impact:** UX, dev
- **Находка:** рамки разрешают действия только там, где они уже есть
  (`/wizard/save`). Пробел §3 п.1 соблазняет добавить кнопку «Accept» в
  баннер — это новая мутация (merge ветки!), выход за read-only.
- **Предлагаемое решение:** никаких серверных мутаций, кроме существующей
  `/wizard/save`. Везде, где нужно действие владельца (гейт, запуск, resume),
  UI показывает **точную команду + кнопку «копировать»** (clipboard API,
  чистый клиент). Явно зафиксировать: кнопка «Accept из браузера» возможна
  только отдельной директивой владельца с правкой §4.1.
- **Правки спеки:** §4.1 — дополнить: «копирование команд в буфер — не
  мутация»; §1.1.7 — сценарий с баннером и copy.
- **Альтернатива:** добавить `POST /accept` — отклонено по умолчанию;
  нарушает зафиксированную рамку read-only к runs/ и git-операции из
  веб-процесса без терминала.

## Q-07. Журнал без горизонтального скролла + адаптивная панель

- **Severity:** major · **Impact:** UI
- **Находка:** §3 п.14: панель min 420 px и колонки min 220 px требуют
  горизонтальной прокрутки; `<pre>` с `white-space: pre-wrap` спасает не
  всегда — длинные команды/URL без пробелов разрываются некрасиво, а на
  узком экране панель 46% перекрывает канбан.
- **Предлагаемое решение:**
  - события — не сплошной `<pre>`, а список компактных блоков: строка меты
    (ts · фаза/роль · exit · токены/$) + команда в mono-блоке с
    `overflow-wrap: anywhere` + note с отступом;
  - панель: ≥1200 px — 40% справа (min 400 px); <1200 px — overlay на весь
    экран с закрытием по ✕ и Esc;
  - канбан на <768 px: колонки не сжимаются ниже 240 px, контейнер —
    горизонтальный scroll-snap по колонкам (это честный паттерн для канбана,
    а не «всё влезло»);
  - лимит note в events API поднять 500 → 2000 с клиентским «развернуть»
    (read-only изменение; tail-лимиты не трогаем).
- **Правки спеки:** §2.2 (панель — адаптивная), §4.8 (note в events — 2000,
  в карточках — 500), §3 п.14 — закрыт частично (канбан snap, панель overlay).
- **Альтернатива:** оставить `<pre>` и добавить только `overflow-wrap` —
  дешевле, но команды по-прежнему смешаны с мета-данными в одну простыню.

## Q-08. Wizard-форма: рестайл без новой функциональности

- **Severity:** minor · **Impact:** UI
- **Находка:** `/wizard` — серверный рендер, единственная мутация UI. Остаётся
  в старом стиле, если не включить в итерацию — визуальный разрыв с канбаном.
- **Предлагаемое решение:** включить в макеты: те же токены site/, карточки
  задач, lint-предупреждения как alert-полосы, RU/EN, кнопка «Сохранить
  черновик» — акцентная. Архитектура не меняется (отдельная серверная
  страница, POST /wizard/save). Функциональность — строго текущая (без
  add/remove/depends_on, см. Q-05).
- **Правки спеки:** §2.1 (строка wizard — без изменений по данным/действиям).
- **Альтернатива:** не трогать wizard в v1 — экономия ~1 экрана мокапов,
  ценой несогласованного вида.

## Q-09. Живость данных: индикатор обновления и потери соединения

- **Severity:** minor · **Impact:** UX
- **Находка:** §1.1.4/§2.2: fetch-ошибки глотаются молча (`catch { return }`)
  — при упавшем сервере владелец смотрит на устаревший канбан, считая его
  живым. Противоречит «честности» инструмента.
- **Предлагаемое решение:** в шапке — «обновлено HH:MM:SS» с зелёной точкой;
  при ошибке fetch — точка красная + «соединение потеряно, повтор…», данные
  остаются, но помечены устаревшими. Polling при скрытой вкладке ставится на
  паузу (`visibilitychange`), при возврате — немедленное обновление.
- **Правки спеки:** §2.2 — пункт про индикатор и паузу polling.
- **Альтернатива:** молчаливые retry как сейчас — бесплатно, но нечестно.

## Q-10. Кнопка «Выполнить» для гейт-команды + модальное окно последствий

- **Severity:** major · **Impact:** UX, dev · **Статус:** одобрено владельцем
  на финальном гейте 2026-08-26 («нужно доработать… кнопка для выполнения
  этой команды, с указанием последствий отдельным модальным окном»).
  **Изменяет Q-06:** рядом с «копировать» появляется серверная мутация.
- **Решение (по директиве):**
  - В баннере gate-wait и в блоке «простым языком» — две кнопки:
    «копировать» (как было) и **«Выполнить…»** (primary, accent).
  - «Выполнить…» открывает **модальное окно подтверждения** с тремя
    секциями:
    - **Что делали** — сводка по задаче из журнала: пайплайн
      (coder → validate → review), стоимость, repair-итерации, ветка
      `forge/<task_id>`, коммит;
    - **Что сделано** — задача в `done`, reviewer одобрил, ветка
      закоммичена локально, прогон приостановлен на гейте №3;
    - **Что будет сделано при одобрении** — `forge accept <id>`: merge
      ветки `forge/<id>` в текущую ветку целевого репо, задача пишется в
      `accepted` в run.json; затем `forge resume <run>`: прогон продолжится,
      следующие задачи очереди начнут выполняться и **тратить бюджет** (в
      пределах капов). Предупреждение: при merge-конфликте accept завершится
      ошибкой и прогон останется на гейте.
  - Кнопки модального: «Отмена» (default, Esc) и «Подтвердить: accept +
    resume» (accent). Подтверждение → состояние «выполняется…» (спиннер,
    кнопки disabled) → успех: модальное закрывается, баннер исчезает на
    следующем polling → ошибка: красная полоса в модальном с текстом
    stderr, модальное остаётся открытым.
  - **API (новые мутации, первые после /wizard/save):**
    - `POST /api/run/<run_id>/accept` `{task_id}` — выполняет accept
      (та же логика, что `forge accept`: merge + запись в accepted);
      409 при merge-конфликте, 404 при невалидном run/task;
    - `POST /api/run/<run_id>/resume` — запускает `forge resume <run_id>`
      субпроцессом (detached, лог в `runs/<id>/resume-ui.log`), сразу 202;
      409, если прогон уже выполняется (lock-файл раннера).
    - UI вызывает accept, при успехе — resume. Обе ручки пишут в `runs/`
      **через существующие механизмы runner'а**, не напрямую.
  - Ограничения безопасности без изменений: localhost-only, без auth —
    инструмент владельца (§4.3).
- **Правки спеки:** §2.1 (две новые POST-ручки), §4.1 (список мутаций:
  wizard/save + accept + resume), §1.1.7 (сценарий с кнопкой и модальным),
  §3 п.1 — формулировка «гейт из браузера» закрыт полностью.
- **Альтернатива (отклонена владельцем):** только copy-команды (исходный
  Q-06).

## Q-11. Мобильный канбан: варианты вместо горизонтального scroll-snap

- **Severity:** major · **Impact:** UX, UI · **Статус:** РЕШЕНО — владелец
  выбрал **вариант B (аккордеон)** на финальном гейте 2026-08-26. Вариант A
  остаётся задокументированной альтернативой.
- **Вариант A — «Чипы состояний + один список» (рекомендуемый):**
  горизонтальная прокручиваемая полоса чипов `Состояние · N` поверх одного
  вертикального списка карточек выбранного состояния. Дефолтный чип —
  «требующий внимания»: gate-wait → failed/blocked → running → done.
  Плюсы: одна ось прокрутки (только вертикаль), карточки на всю ширину
  экрана (note и статы читаемы), быстрый доступ к любому состоянию в 1 тап,
  счётчики видны всегда. Минус: не видна «труба» целиком — компенсируется
  прогресс-баром «N из M» в шапке.
- **Вариант B — «Аккордеон пайплайна»:** вертикальный список секций в
  порядке пайплайна; заголовок секции = состояние + счётчик + шеврон;
  раскрытие показывает карточки. Дефолтно раскрыта секция внимания,
  остальные свернуты; раскрывать можно несколько. Плюсы: сохраняет
  ментальную модель пайплайна и обзор всех состояний в одном скролле.
  Минусы: длинный скролл при многих раскрытых секциях, карточки уже, чем
  в A, при раскрытом drawer-overlay смысл секций теряется.
- **Общее для обоих:** drawer — полноэкранный overlay; баннер gate-wait
  прижат кверху; свайп/жесты не вводим (нативный скролл надёжнее).
- **Правки спеки:** §2.2 и §3 п.14 — мобильный канбан: **аккордеон (B) —
  основной паттерн** (выбор владельца 2026-08-26), чипы (A) —
  задокументированная альтернатива.
- **Альтернатива (отклонена):** горизонтальный scroll-snap по колонкам —
  две оси прокрутки, узкие карточки, колонки вне viewport не видны.
