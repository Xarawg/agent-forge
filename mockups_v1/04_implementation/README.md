# Стадия 4 — план реализации продакшн-UI (v1)

Основание: `../02_ux/ux-spec.md` (гейты пройдены 2026-08-26, Q-01…Q-11
resolved). Эталон вёрстки: `../03_ui/ui-board.html`.

**`tasks.ui-v1.yaml` — черновик очереди agent-forge для реализации.** Это
гейт №1 по процессу самого agent-forge: перед запуском черновик проверяется
человеком (`forge lint tasks.ui-v1.yaml`, правка через `/wizard`), затем
`forge run --tasks tasks.ui-v1.yaml --target .`. Живые прогоны на этом этапе
не запускались.

## Волны реализации (DAG)

```
Волна 1 — API (read-only расширение + мутации Q-10)
  api-queue-gatewait ──┬─> api-report-extra
                       └─> api-accept-resume [gate: api]

Волна 2 — ядро UI
  ui-skeleton-i18n ──> ui-kanban ──┬─> ui-gate-modal [gate: ui-actions]
                                   ├─> ui-report-tab
                                   └─> ui-drawer
  ui-skeleton-i18n ──> ui-wizard-restyle

Волна 3 — адаптив, тесты, доки
  ui-mobile-accordion (после modal+report+drawer)
  tests-ui-v1 (после mobile + wizard-restyle)
  docs-spec-sync [gate: docs]
```

Почему так: скелет с токенами/i18n — общий фундамент всех видов; модальное
accept/resume зависит и от канбана (баннер), и от POST-ручек; мобильный
аккордеон трогает все виды, поэтому последним; тесты пишутся отдельной
задачей на уже реализованное поведение (заморозка acceptance, см. ниже);
доки — после кода, чтобы спека описывала факт.

## Заморозка acceptance (решение по lint)

`forge lint` (прогнан 2026-08-26, запускается) дал два класса советов:

1. **Тесты в scope coder'а** — убрано: ни одна задача реализации не пишет в
   `tests/`. Новые регрессионные тесты собраны в отдельной задаче
   `tests-ui-v1` (предупреждение там неизбежно и осознанно: задача пишет
   тесты на уже реализованное поведение, сверяясь с ux-spec §3).
2. **«acceptance запускает тесты, которых никто не пишет»** — ложное для
   нашего репо: `tests/test_ui.py` и `tests/test_ui_wizard.py` существуют и
   зелёные (проверено: 15 passed). Acceptance реализационных задач —
   «существующий набор остаётся зелёным» + grep-проверка офлайн-чистоты
   статики; покрытие новых полей — зона `tests-ui-v1`.

## Гейты №3 (human accept) в очереди

| Задача | Что проверить перед accept |
|---|---|
| `api-accept-resume` | мутации идут через runner/journal, не напрямую; 409 при merge-конфликте и при активном lock; resume пишет `resume-ui.log`; `runs/` вне accept/resume не меняется |
| `ui-gate-modal` | модальное §4.3: три секции, блокировка закрытия в «busy», ошибка не закрывает окно; copy-кнопка рядом сохранена |
| `docs-spec-sync` | спека описывает фактическое поведение; §3-пробелы помечены закрытыми корректно; англ. версия синхронна |

## Риски и как они закрыты в задачах

1. **POST accept — merge-конфликт в целевом репо.** Accept обязан вернуть
   409 + stderr, не оставляя репо в половинчатом состоянии (merge --abort в
   обработчике). Тест на конфликт — в acceptance задачи.
2. **Двойной resume.** Lock-файл раннера — единственный источник истины;
   UI не ведёт свой флаг «прогон идёт».
3. **Офлайн-чистота статики.** Acceptance каждой UI-задачи включает
   `! grep -Eq "https?://|@import" forge/ui_static/index.html`.
4. **Полнота i18n.** Все новые строки — только через словарь `I18N`;
   проверка на гейте `ui-gate-modal` и `docs-spec-sync` (переключатель
   RU/EN на каждом виде, включая модальное и wizard).
5. **Регрессии существующего API.** Поля `tasks`/`totals` не меняются —
   обратная совместимость проверяется существующим `tests/test_ui.py`,
   который обязан остаться зелёным без правок (кроме добавления новых
   кейсов).
