## 2. Что нужно сделать (подтверждённые разрывы)

### A. Онбординг и документация

- **A1. RU-версия сайта ссылается на английские .md** — футер сайта статичен и ведёт на `SPEC.md`, хотя есть `SPEC.ru.md` и т.д. Нужен `data-i18n-href` (переключение href по языку) или отдельные ссылки «RU» рядом.
- **A2. Нет `forge init`** — «подготовить проект» сейчас означает ручное копирование конфигов. Нужна команда: проверить git-репо, создать skeleton `tasks.yaml`, проверить `.env`/ключи, напечатать следующие шаги.
- **A3. Нет пошагового руководства по трём потокам** — «подготовить проект → подготовить план → запустить агентов» с копируемыми командами. README Quickstart покрывает это фрагментарно. Нужен `docs/WORKFLOWS.md` (+ `.ru.md`).

### B. Управляемость исполнения

- **B1. Нет stop/pause** — сейчас остановить прогон можно только убив процесс. Нужен кооперативный стоп: `forge stop <run_id>` создаёт маркер `runs/<id>/STOP`, runner проверяет его между задачами и между repair-итерациями, UI получает кнопку (POST). Kill остаётся аварийным вариантом — resume уже умеет продолжать.
- **B2. Нет pipeline-вида «как в GitLab CI»** — kanban показывает состояние задачи, но не стадии внутри неё (coder → validate → review → repair×N) и не логи по каждой стадии отдельно. Все данные уже есть в `events.jsonl` (поле `phase`); нужен рендер стадий в UI с раскрывающимися логами.

### C. Изоляция (сандбокс)

- **C1. Команды исполняются на хосте.** Задокументировано в SECURITY.md как «guardrail, not sandbox». Целевая постановка пользователя: проект погружается в закрытый Docker-контейнер, код дописывается и логируется там. Минимально жизнеспособный вариант в текущей архитектуре: `sandbox: docker` в конфиге → per-run контейнер (`python:3.12-slim` или образ из `sandbox.image`), target смонтирован rw, **network: none**, `run_command` и acceptance исполняются через `docker exec`; при отсутствии Docker — host-исполнение с явным варнингом в журнал. Риск: acceptance у реальных проектов часто требует сеть/зависимости (npm test с кэшем, NuGet) — поэтому network policy делаем конфигурируемой (`none|restricted|full`).

### D. Качество кодогенерации (долги из DECISIONS)

- **D1. Reviewer получает дамп файлов вместо diff** (AF-02, «Debt v2»): когда target — git-репо, прикладывать `git diff` ветки задачи. Дешёвое и большое повышение качества ревью.
- **D2. Нет repo-map** — coder тратит шаги на разведку структуры. Лёгкая карта (заголовки/сигнатуры файлов scope) в промпт coder'а.

### E. Дистрибуция

- **E1. Нет PyPI/релизов** — установка только из клона. `pyproject.toml` уже готов к публикации; нужен release-workflow.

## 3. Что можно сделать (оценка реализуемости)

Всё из §2 реализуемо **без смены архитектуры**:

- A1–A3, B1, B2, D1 — чистая работа в существующих модулях (`cli.py`, `runner.py`, `ui.py` + vanilla-JS статика; SPEC требует stdlib-only UI — соблюдаемо).
- C1 — единственный пункт с внешней зависимостью (Docker Desktop на Windows-хосте). Делаем опциональным: host-режим остаётся дефолтом, что сохраняет NFR-1 (без админ-прав).
- D2 — без tree-sitter: регексп-карта сигнатур достаточна для v1 и не добавляет зависимостей.

Что осознанно **не** делаем в этой волне: параллелизм DAG (SPEC §7 — v2), MCP-интеграции, публичный бенчмарк (AF-13), push/PR-автоматизация (нарушает NFR-5).

## 4. Как прийти: план исполнения

Исполнитель — **сам agent-forge поверх DeepSeek** (dogfooding): очередь `config/tasks.v2.yaml`, целевой репозиторий — сам agent-forge.

```
Волна 1 (доки, быстрые победы, gate):
  t1 docs-workflows      A3  → docs/WORKFLOWS.md (+ru), ссылки из README
  t2 site-ru-links       A1  → i18n-href на сайте          [gate: wave-1]

Волна 2 (управляемость, gate):
  t3 forge-init          A2  → команда forge init
  t4 stop-control        B1  → forge stop + UI-кнопка
  t5 pipeline-view       B2  → стадии и логи в UI (depends_on: t4)  [gate: wave-2]

Волна 3 (качество и изоляция, gate):
  t6 git-diff-reviewer   D1  → git diff в промпт reviewer (depends_on: t4)
  t7 sandbox-docker      C1  → docker-executor (depends_on: t6)     [gate: wave-3]

Волна 4:
  t8 repo-map-context    D2  → карта репо в промпт coder
```

Запуск (после поднятия `per_run_max_cost_usd` в `config/models.yaml` с $2.00 до ~$6.00 — очередь из 8 задач в текущий кап не помещается):

```bash
forge run --tasks config/tasks.v2.yaml --target . --spec docs/GAP_ANALYSIS.ru.md
forge status        # наблюдение; UI: forge ui
forge accept t2-site-ru-links   # после волны 1
forge resume <run_id>
# ... и так по гейтам
```

Каждая задача — своя ветка `forge/<id>`, локальные коммиты, ревью человеком на гейтах волн. Ожидаемая стоимость прогона на текущих ценах DeepSeek (provod.ai): ~$3–5.

## 5. Критерии приёмки волны в целом

1. Все 8 задач в `done` (или осмысленный `failed` с журналом), `pytest -q` зелёный на каждом гейте.
2. `forge init` в пустом каталоге → готовый skeleton за одну команду.
3. В UI видны стадии задачи и их логи; кнопка Stop останавливает прогон между шагами без kill.
4. `sandbox: docker` — acceptance задачи исполняется внутри контейнера (видно по журналу), без Docker — варнинг и host-режим.
5. Сайт: RU-переключатель ведёт на русские версии доков.
