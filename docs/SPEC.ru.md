# SPEC — agent-forge: инфраструктура агентной кодогенерации

Версия 1.2 · Спецификация самого инструмента (адаптирована из исходного пакета
спецификации; убрана привязка к конкретному продукту/монорепо). v1.2: правка NFR-2
(AF-14 server-режим), ссылки на роадмап v2/v3 (§7).

## 1. Цель

Инструмент (`agent-forge`), который владелец запускает локально (Windows-first) и который:

1. Читает пакет спецификации (SPEC.md) и очередь задач `tasks.yaml`.
2. Разбивает пакет на задачи и гоняет их через **LLM-агентов на OpenAI-совместимом API** (пресеты: DeepSeek direct, бесплатные модели OpenRouter `*:free`, локальные через Ollama-совместимый endpoint; любой другой — своим пресетом в `config/providers/`).
3. Контролирует ход разработки: журнал прогонов, состояния задач, бюджетные капы, валидация результата, человеческий гейт между милстоунами.
4. Работает поверх произвольного целевого репозитория (`--target`), делая ветку на задачу и локальные коммиты; push — только владельцем вручную.

НЕ цель: заменить CI целевого репозитория; играть роль IDE-плагина; генерировать код без спеки (agent-forge всегда стартует от спецификации/очереди задач, написанной человеком).

## 2. Роли и модели

| Роль | Назначение |
|---|---|
| planner | пакет → черновик плана задач (DAG) |
| coder | пишет код по задаче |
| reviewer | ревью результата по чек-листу |
| repair | починка по выводу валидаторов |

Модельная карта — в конфиге (`config/models.yaml`), не в коде. Один провайдер = base_url + api_key; смена модели = правка конфига. Пресеты провайдеров — `config/providers/*.yaml`; модели ролей и цены (USD за 1M токенов) — `config/models.yaml`.

## 3. Функциональные требования

### FR-1. Импорт пакета
Читает `SPEC.md` пакета и формирует черновик задач через planner-роль (`forge import`); владелец правит `tasks.yaml` руками до запуска (человеческий гейт №1). Формат задачи — `config/tasks.example.yaml` (id, title, spec_ref, scope_paths[], depends_on[], acceptance[], budget, gate).

### FR-2. Агентный цикл coder
По задаче: собирает контекст (выдержка спеки + опциональный canon-снапшот + файлы scope) → промпт из `prompts/50_task_template.md` → цикл «модель ↔ инструменты» до заявки «готово» или исчерпания шагов. Инструменты агента: `read_file`, `write_file`, `list_dir`, `run_command` (whitelist: python, pytest, npm, node, dotnet, ruff, mypy; установка зависимостей запрещена на уровне инструмента). Коммит агенту не выдаётся — коммитит runner после гейта reviewer. Scope-ограничение: write_file только в `scope_paths` задачи.

### FR-3. Валидация результата (гейт №2, автоматический)
После coder: прогон `acceptance`-команд задачи (тесты/линт/валидаторы — доверенные, их пишет владелец) → reviewer-роль оценивает результат по чек-листу `prompts/30_reviewer.md` → fail уходит в repair-цикл (максимум N=3 итераций, далее задача в `failed` с журналом). Repair-агент может завершиться маркером `STUCK` (→ failed) или `DISPUTE` (→ blocked: противоречие в спеке решает человек, а не модель).

### FR-4. Контроль хода (для владельца)
- Журнал прогонов: `runs/<run_id>/events.jsonl` — каждое событие (вызов модели, токены, команда, результат).
- Состояния задач: `queued → running → validating → review → done | failed | blocked` (repair-итерация = повторный `running`, счётчик в состоянии задачи).
- CLI-команды: `forge status` (таблица задач прогона), `forge log <task_id>`, `forge resume <run_id>` (продолжить после остановки), `forge report` (сводка: токены, стоимость, сроки).
- Веб-UI `forge ui`: канбан состояний, лог-вьюер событий задачи, отчёт по прогону; только чтение `runs/`.
- Человеческий гейт №3: merge ветки задачи — только по явной команде `forge accept <task_id>`.

### FR-5. Бюджетные капы
Per-task (max_tokens / max_cost_usd), per-run (max_cost_usd), per-day (max_cost_usd, сумма по журналам всех прогонов за сутки UTC). Превышение → задача в `blocked`, причина в журнале. Лимиты провайдера (RPM/5xx) отрабатываются retry с экспоненциальным backoff (`retry` в models.yaml) и перебором `fallback_models` пресета.

### FR-6. Конфигурация провайдеров
`.env` / окружение: `FORGE_PLANNER_BASE_URL/API_KEY/MODEL`, … по ролям; общий fallback `FORGE_BASE_URL` / `FORGE_API_KEY`. Дефолтный пресет — `config/providers/deepseek.yaml`; выбор — `--provider` или `FORGE_PROVIDER`. Mock-режим: `FORGE_MOCK=1`.

### FR-7. Воспроизводимость
Каждый прогон фиксирует в `run.json`: модели ролей, версию промптов (git hash prompts/, вне git — sha256 содержимого), провайдера, mock-флаг. Отчёт `forge report` включает цену прогона по прайсу из конфига.

## 4. Нефункциональные требования

- NFR-1: Windows 10/11 + Git Bash; без админ-прав; Python 3.12+.
- NFR-2: Никаких фоновых демонов — одна команда = один прогон; состояние на диске (можно убить процесс и `forge resume`; снапшоты истории диалога в `tasks/<id>.<phase>.history.json`). Веб-UI — отдельный процесс только для чтения. **Правка AF-14 (2026-08-21):** допускается опциональный демон `forge serve` (FastAPI, extra `[server]`); журналы на диске остаются единственным источником истины в обоих режимах. См. docs/ARCH_TARGET.ru.md §3.1.
- NFR-3: Секреты только в `.env` (в .gitignore); логи не содержат ключей.
- NFR-4: Стоимость прогона пилотной задачи на платной модели ≤ $0.50; на free-моделях — $0 (лимиты RPM учитываются backoff'ом).
- NFR-5: agent-forge не пушит в удалённый git сам; ветка + локальный коммит — да, push — нет.

## 5. Модель данных

```
tasks.yaml        — очередь задач пакета (см. config/tasks.example.yaml)
runs/<run_id>/    — run.json (метаданные), events.jsonl (журнал), tasks/<id>.json (состояние, итерации repair)
prompts/          — библиотека промптов (версионируется git'ом)
config/           — models.yaml, providers/*.yaml, tasks.example.yaml
```

Событие журнала: `{ts, run_id, task_id, phase, role, model, tokens_in, tokens_out, cost_usd, command?, exit_code?, note}`.

## 6. Критерии приёмки

1. Прогон end-to-end на реальном провайдере: задача доходит до `done` или осмысленного `failed`; `forge status`/`report` показывают ход; стоимость в пределах капа.
2. Mock-режим (`FORGE_MOCK=1`): весь цикл без API-ключа — для CI и разработки самого agent-forge.
3. Repair-цикл: намеренно сломанная приёмка чинится ≤3 итераций или задача уходит в `failed` с понятным журналом.
4. Scope-контроль: попытка coder'а писать вне `scope_paths` блокируется и логируется.
5. Тесты agent-forge запускаются одной командой; Docker-образ собирается; README покрывает local/Docker/Linux.

## 7. Ограничения и анти-паттерны

- Не давать coder-роли доступ в `canon/` на запись (каталог `canon/` в целевом репо — всегда read-only для агента; кодогенерация читает canon, правит его только владелец).
- Не изобретать промпты в коде — вся текстовка промптов живёт в `prompts/` (версионируется, ревьюится).
- Не скрывать сырые ответы моделей — events.jsonl полный (кроме секретов).
- Не плодить параллелизм v1: задачи идут последовательно (free-лимиты); параллельность — NFR на v2.
  **Роадмап (2026-08-21):** очередь v2 — `config/tasks.v2.yaml` (разрывы по docs/GAP_ANALYSIS.ru.md); очередь v3 — `config/tasks.v3.yaml` (целевая архитектура по docs/ARCH_TARGET.ru.md: server-режим, executor-плоскость с remote docker, контекст/evals/наблюдаемость). Параллелизм внутри DAG — волна D v3 (сначала multi-run); человеческие гейты между волнами обязательны.
