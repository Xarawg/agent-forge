## Контекст проекта

agent-forge — open-source (MIT) оркестратор серийной LLM-кодогенерации: очередь спек-задач (tasks.yaml, DAG) гоняется через OpenAI-совместимых провайдеров (DeepSeek и др.) с гейтами качества: acceptance-команды (реальные тесты) → ревью второй моделью → repair-цикл ≤3 → человеческие гейты между волнами. Жёсткие бюджетные капы в USD (per-task/run/day), полный аудит на диске (events.jsonl), resume после kill, mock-режим для CI. Позиционирование: не pair-programmer (aider) и не облачный автоном (Devin), а **управляемая batch-очередь с финансовыми гарантиями, local-first**.

Запланирована эволюция до v3: server-режим с UI из Docker (FastAPI, control plane), исполнение на удалённых хостах через `DOCKER_HOST=ssh` (execution plane, LLM-ключи не покидают control plane), эмбеддинги + sqlite-vec для контекста, приватный eval-харнес, Prometheus/OTLP-наблюдаемость. Реализация — dogfooding: сам agent-forge пишет код через DeepSeek по очередям задач с человеческими гейтами.

## Что оценить (критерии)

1. **Архитектурная состоятельность**: разделение control/execution plane, executor-протокол, журналы-как-истина + SQLite-индекс, server-режим поверх one-shot CLI. Где переусложнение? Где недопроектировано?
2. **Конкурентная позиция**: реально ли заявленная ниша (governed batch codegen с USD-капами и human gates) защищаема против aider/OpenHands/Plandex/Claude Code/Kiro/Devin? Что из v3-плана закрывает разрыв, а что — бесполезная имитация фич лидеров, которые они сделают лучше?
3. **Dogfooding-план**: реалистично ли, что такие очереди (tasks.v2/v3, задачи по $0.4–1.0, DeepSeek v4) дадут production-код? Где задачи слишком крупные/мелкие, где acceptance не проверяет главное?
4. **Риски**: безопасность (executor, remote, токены), надёжность (resume, рестарт сервера), эксплуатация (Windows-first + Docker), одно-мейнтейнерский проект.
5. **Что выкинуть**: какие элементы v2/v3 — преждевременные или лишние для инструмента такого масштаба (честно: evals? observability? sqlite-vec? multi-run?).

## Формат ответа

1. **Вердикт** (5–7 предложений): станет ли это топовым инструментом в своей нише при исполнении плана, и главное «но».
2. **Сильные стороны архитектуры** — что не трогать.
3. **Изменить** — таблица: элемент | проблема | конкретное изменение | приоритет (P0/P1/P2).
4. **Выкинуть или отложить** — с обоснованием.
5. **Чего не хватает** — чего нет ни в v1, ни в планах, а у топового инструмента должно быть.
6. **Оценка dogfooding-плана** — пройдёт/не пройдёт по волнам; где человек обязан писать код сам.

Пиши по-русски. Будь конкретен: ссылаться на файлы/разделы, не на общие места. Если какая-то часть плана слабее конкурентов по устройству — скажи прямо, у кого сделано лучше и как именно.
