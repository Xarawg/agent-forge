## 1. Целевая постановка (от владельца)

Инструмент с UI, развёрнутым из Docker, который управляет кодогенерацией — вплоть до сценария, где **агенты генерируют код на удалённом хосте**, а владелец наблюдает и управляет через браузер.

## 2. Что меняется концептуально: control plane / execution plane

Текущая v1 — один CLI-процесс, всё локально, состояние на диске. v3 разделяет:

```
┌─────────────────────────────────────────────────────────────┐
│ CONTROL PLANE (Docker-контейнер на машине владельца)        │
│                                                             │
│  forge serve ──► HTTP API (REST + SSE-стрим событий)        │
│               ──► Web UI (интерактивный, не read-only)      │
│               ──► Планировщик прогонов (Runner как сервис)  │
│               ──► LLM-клиенты (ключи ТОЛЬКО здесь, в .env)  │
│               ──► Журналы runs/ + SQLite-индекс             │
└──────────────────────┬──────────────────────────────────────┘
                       │ executor-протокол (команды/файлы/события)
        ┌──────────────┼──────────────────┐
        ▼              ▼                  ▼
  EXEC: host     EXEC: docker       EXEC: docker-remote
  (как сейчас)   (локальный         (DOCKER_HOST=ssh://…
                 контейнер,          или SSH-транспорт:
                 network policy)     код и команды уезжают
                                     на удалённый хост,
                                     LLM-ключи — НЕТ)
```

**Ключевое архитектурное свойство:** LLM-ключи и разговор с моделью остаются на control plane. На удалённый хост уезжают только файлы и команды — утечка креденшелов провайдера через скомпрометированный таргет исключена.

## 3. Что конкретно нужно сделать/изменить

### 3.1. Server-режим (ломает NFR-2 — требуется решение AF-14)

- **AF-14 (предложение):** два режима. CLI one-shot остаётся навсегда (CI, разработка, NFR-2 для v1-совместимости). `forge serve` — опциональный демон для интерактивной работы. Это не отказ от «состояние на диске»: журналы остаются source of truth, сервер переживает рестарт чтением `runs/`.
- Runner уже класс — сервер держит активные прогоны в потоках, по одному на `forge run`. Кооперативный stop/pause (волна v2, t4) — обязательная предпосылка.
- Стек: FastAPI + uvicorn как **опциональная зависимость** (`pip install agent-forge[server]`); ядро остаётся stdlib-only. Текущий read-only UI (`ui.py`, stdlib) мигрирует в server как набор эндпоинтов без изменения контракта.

### 3.2. Состояние: журналы + SQLite-индекс

- `events.jsonl` / `tasks/<id>.json` остаются append-only источником истины (аудит, resume, NFR-2).
- Поверх — SQLite-индекс (`runs/index.db`): таблицы runs/tasks/costs для быстрых выборок UI (dashboard, фильтры, per-day капы без полного обхода файлов). Индекс **пересобираем** из журналов (`forge reindex`) — это защита от рассинхрона.

### 3.3. API и интерактивный UI

- REST: `POST /api/runs` (запуск), `POST /api/runs/<id>/stop|resume`, `POST /api/tasks/<id>/accept`, существующие GET (список прогонов, события, отчёты).
- SSE-стрим `/api/runs/<id>/events/stream` — живой pipeline в браузере без поллинга (сейчас meta-refresh 3s).
- Auth: один токен из env (`FORGE_UI_TOKEN`), header-проверка; bind по умолчанию на 127.0.0.1. Multi-user не делаем (см. §6).
- UI: те же статика без сборки, но с контролами: запуск прогона из формы (tasks.yaml из репо), стоп/резюме, accept на гейтах, живые стадии (волна v2, t5), стоимость по провайдерам/дням.

### 3.4. Executor-абстракция (сердце v3)

```python
class Executor(Protocol):
    def write_file(rel, content) -> ...   # с scope-контролем, как сейчас
    def read_file(rel) -> str
    def list_dir(rel) -> str
    def run_command(cmd) -> (exit_code, output)   # allowlist + deny-паттерны
    def run_acceptance(cmd) -> (exit_code, output)  # доверенные команды владельца
```

- `HostExecutor` — текущее поведение (рефакторинг ToolBox в интерфейс).
- `DockerExecutor` (волна v2, t7) — локальный демон, network-политика.
- `RemoteDockerExecutor` — **тот же DockerExecutor против удалённого демона**: `DOCKER_HOST=ssh://user@host`. Один код сандбокса, локальный или удалённый демон — это самый дешёвый путь к «агенты на удалённом хосте» без своего протокола и агента-демона.
- Альтернатива/дополнение позже: `SSHExecutor` (rsync + ssh-команды) для хостов без Docker. Не в первой волне.

### 3.5. Git при удалённом исполнении

Код пишется на удалённом хосте → ветки `forge/<id>` и коммиты создаются там. Решение (предложение для спеки): remote-клон — рабочая копия; `forge accept` делает `git fetch` с удалённого remote (хост добавляется как git remote по SSH) + `--no-ff` merge локально. NFR-5 (никакого push) сохраняется: fetch — это pull-направление.

### 3.6. Параллелизм (закрытие долга SPEC §7 v2)

С пулом executor'ов независимые ветви DAG могут идти параллельно (по контейнеру на задачу). В v3: сначала параллелизм на уровне прогона (несколько runs), затем внутри DAG — отдельным решением после стабилизации server-режима.

### 3.7. Дистрибуция

- Образ `agent-forge` на ghcr.io (CI публикует по тегу), docker-compose: server + тома (`runs/`, `config/`, `.env`) + порт UI.
- PyPI-пакет с extras `[server]`.

## 4. Что потянет кодогенерация своими силами (agent-forge на DeepSeek)

| Слой | Пригодность для codegen | Почему |
|---|---|---|
| Executor-интерфейс + HostExecutor-рефакторинг | ✅ высокая | чёткий контракт, существующие тесты как acceptance |
| DockerExecutor + RemoteDocker (DOCKER_HOST=ssh) | ✅ высокая | механика docker CLI хорошо специфицируется; тесты через фейк-демон |
| REST API поверх Runner + SSE | ✅ высокая | типовой слой; acceptance — pytest + curl-проверки |
| SQLite-индекс + reindex | ✅ высокая | детерминированная схема, проверяется тестами |
| UI-контролы и живой pipeline | ✅ средне-высокая | статика без сборки; acceptance — pytest на API + ручное ревью на гейте |
| Auth-токен, конфиг server-режима | ✅ высокая | маленький изолированный код |
| **Failure-семантика сети/SSH, гонки стопа, схема состояний сервера** | ⚠️ **человек проектирует** | распределённые edge-cases; codegen реализует по точной спеке, но спеку пишет владелец |
| **Протокол executor, миграция журналов, решения AF-14+** | ⚠️ человек | это контракты; ошибка здесь дороже всего |

**Вывод:** ~80% объёма v3 — codegen-пригодно при условии, что контракты (executor-протокол, API, состояния) зафиксированы в спеке до запуска волн. Именно поэтому сначала этот документ, потом tasks.v3.yaml.

## 5. Волны v3 (после завершения v2)

```
Wave A (server skeleton):    serve + REST read + SSE + запуск прогона в потоке
Wave B (control):            stop/resume/accept через API, токен-auth, UI-кнопки
Wave C (remote execution):   Executor-рефакторинг → DockerExecutor → DOCKER_HOST=ssh
                             + git fetch-модель для accept
Wave D (state & scale):      SQLite-индекс, multi-run dashboard, параллельные runs
Wave E (distribution):       ghcr.io образ, compose, PyPI [server]
```

Оценка: 12–16 задач agent-forge, ~$10–15 на DeepSeek-ценаx provod.ai, 4–5 человеческих гейтов. Реалистичный горизонт своими силами — волны A–C дают ровно целевую постановку §1; D–E — по мере использования.

## 6. Расширенные волны: контекст, evals, наблюдаемость (добавлено 2026-08-21)

```
Wave F (context & retrieval):   эмбеддинги + векторное хранилище + гибридный контекст
Wave G (evals):                 eval-харнес, золотые наборы, A/B по промптам/моделям
Wave H (observability):         метрики, Prometheus-эндпоинт, OTLP-трейсинг, вебхуки
```

## 7. Границы разумного (чего НЕ делаем)

- Не k8s-оркестратор и не multi-tenant SaaS — один владелец, один сервер, N хостов.
- Не свой фронтенд-фреймворк/сборка — статика без build-шага остаётся принципом.
- Не свой агент-демон на удалённом хосте, пока хватает `DOCKER_HOST=ssh` (меньше кода — меньше атак).
- Не отказ от CLI и не отказ от журналов на диске — server-режим надстройка, не замена.
- Не внешние векторные сервисы (Qdrant/pgvector) в v3 — sqlite-vec в файле.

## 8. Контекст и retrieval: эмбеддинги, векторное хранилище, промпты

Мотивация: coder тратит шаги на разведку репозитория (GAP §2-D2); repo-map (v2, t8) — лексический минимум. Следующий уровень — семантический retrieval.

### 8.1. Хранилище

- **sqlite-vec** (расширение к SQLite) — однофайловая векторная БД в той же философии, что и журналы: `runs/context.db`. Ноль сервисов, бэкап копированием файла, пересборка из целевого репо в любой момент. Альтернативы (Qdrant/pgvector) — внешний сервис, отклонено для v3 (противоречит «один владелец, ноль инфраструктуры»).
- Чанкование: по файлам scope + `docs/` целевого репо; границы по заголовкам/сигнатурам (регексп-чанкер из t8 переиспользуется), размер ~1–2K символов с перекрытием.

### 8.2. Эмбеддинги

- Роль `embedder` в `config/models.yaml` — тот же OpenAI-совместимый механизм (`/v1/embeddings`), пресет провайдера, цена за 1M токенов. Команда `forge index --target .` строит/обновляет индекс инкрементально (хеш файла → пропуск неизменённых).
- Mock-режим: детерминированный hashing-embedder (без API) — тесты retrieval идут в CI без ключа.

### 8.3. Гибридный контекст в промпте coder'а

Приоритет токен-бюджета задачи: (1) spec-excerpt, (2) repo-map scope, (3) top-k векторных чанков по тексту задачи (k и лимит символов — в конфиге), (4) history repair-итераций. Журналируем, какие чанки попали в промпт (событие `phase=context`) — это нужно и для evals, и для аудита.

### 8.4. Управление промптами

- `prompts/` остаются git-версионируемой библиотекой; `prompts_version` уже пишется в run.json (FR-7) — это фундамент экспериментов: каждый прогон связан с версией промптов.
- Добавляем: метаданные промпта (front-matter: назначение, модель-цель, changelog) и связку «версия промптов → результаты» в evals (§9) — A/B промптов становится запросом к хранилищу результатов, а не ручной аналитикой.

## 9. Evals: оценка качества AI-решений

Не публичный бенчмарк (AF-13 — отклонён), а **приватный per-user eval-харнес**: владелец меряет свои модели/промпты на своих эталонных задачах.

- **Золотые наборы** (`evals/suites/*.yaml`): мини-репо-фикстуры + задачи с известным правильным исходом (acceptance зелёный, reviewer APPROVE) и известными ловушками (задача с противоречием → ожидается DISPUTE, а не галлюцинация; задача вне scope → ожидается блок).
- **`forge eval --suite NAME`**: прогон набора, отчёт в `runs/evals/<id>/`: pass rate, средние repair-итерации, стоимость, доля корректных отказов (DISPUTE/BLOCKED там, где надо). Метрики качества — не «прошло/упало», а поведение на границах.
- **Сравнение**: `forge eval compare <run_a> <run_b>` — таблица по моделям/версиям промптов (данные из run.json: модели + prompts_version). Это ответ на «как настраивать» — меняешь промпт или модель, гоняешь suite, смотришь дельту.
- **CI-гейт**: mock-suite (детерминированный, без API) в CI — регрессия оркестратора ловится на PR; реальные evals — по требованию владельца (деньги).

## 10. Наблюдаемость в продакшене

Журналы уже структурированы — остаётся экспорт:

- **Метрики**: агрегация из журналов + живые счётчики server-режима — токены/стоимость по ролям и моделям, длительность фаз (coder/validate/review/repair), repair rate, blocked/failed rate, utilization бюджетных капов. Эндпоинт `/metrics` (Prometheus text format) на `forge serve`.
- **Трейсинг**: опциональный OTLP-экспорт (`pip install agent-forge[otel]`, opentelemetry-sdk): trace = прогон, span = фаза задачи, атрибуты — модель/токены/exit-коды. В Jaeger/Tempo/Grafana виден весь пайплайн как распределённая трасса.
- **Алертинг**: вебхук (`config: alerts.webhook_url`) на `blocked`/`failed`/превышение per-day капа — POST с кратким контекстом. Достаточно для «наблюдаемости систем в продакшене» на уровне одного владельца.

## 11. AI-функции в продуктах компании (рамка использования)

agent-forge — инструмент разработки, а не рантайм продуктовых AI-фич; его роль в этой рамке:

1. **Ускорение разработки AI-фич в целевых продуктах**: очереди-шаблоны (config/templates/) для типовых работ — «добавить RAG-пайплайн в сервис», «обернуть функцию в tool-calling», «прикрутить оркестрацию» — с готовыми acceptance (тесты эмбеддингового индекса, контрактные тесты tool-схем). Качество держится теми же гейтами: тесты → reviewer → человек.
2. **Референс-реализация**: собственные модули agent-forge (LLM-клиент с retry/fallback, цикл tool calling, оркестрация ролей, бюджеты) — читаемый эталон (~2K строк, strict-mypy), который команда может заимствовать в продукты.
3. **Контур качества**: evals §9 применимы и к продуктовым LLM-фичам — golden suites для RAG (known-answer вопросы) гоняются тем же `forge eval` против целевого репо.
