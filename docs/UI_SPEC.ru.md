# Спецификация веб-UI agent-forge

Источник истины — код: `forge/ui.py` (сервер, API, рендер wizard-формы),
`forge/ui_static/index.html` (канбан, отчёт, панель событий), а также
`forge/cli.py` + `forge/report.py` (команды `status` / `log` / `report`,
показывающие те же данные в терминале).

UI — это команда `forge ui`: локальный веб-сервер на чистом stdlib
(`http.server.ThreadingHTTPServer`), который поднимается на `127.0.0.1`
(порт по умолчанию 8765) и показывает содержимое каталога `runs/`.
Почти всё — только чтение; единственная мутация — перезапись YAML-черновика
очереди в `/wizard` (см. §2).

---

## 1. Персоны и сценарии

### 1.1. Владелец следит за прогоном

Контекст: прогон запущен из терминала (`forge run` / `forge resume`), владелец
хочет видеть прогресс, не читая сырые JSON.

1. Запускает `forge ui` (без API-ключа), открывает `http://127.0.0.1:8765/`.
2. В шапке выбирает прогон из выпадающего списка (по умолчанию — последний
   по имени каталога `run-YYYYmmdd-HHMMSS`). Видит провайдера, признак mock,
   время старта и итоговую стоимость.
3. Смотрит канбан: 7 колонок по реальным состояниям runner'а
   (`queued → running → validating → review → blocked → failed → done`).
   Карточка задачи: title, id, метка гейта `⛳ <gate>`, стоимость, токены
   `in+out`, число repair-итераций, note (обрезан до 500 символов).
4. Страница сама обновляется каждые 3 секунды (fetch с `no-store`, без
   перезагрузки). Открытая панель событий тоже обновляется.
5. Клик по карточке → выезжающая панель справа с журналом событий задачи
   (аналог `forge log <task_id>`): timestamp, фаза, роль, команда, exit-код,
   токены/стоимость, note.
6. Кнопка «Отчёт» → таблица всех задач прогона с итоговой строкой
   (аналог `forge report` без `--plain`).
7. Если прогон встал на гейте — владелец видит задачу в колонке `done` с
   меткой `⛳`, но **подсказки «⏸ forge accept … && forge resume …» в UI нет**:
   она есть только в `forge status` (см. §3).

### 1.2. Владелец правит черновик очереди

Контекст: `forge wizard` / `forge import` создали черновик
`tasks.wizard.yaml`; перед запуском (гейт №1) его надо проверить и поправить.

1. Открывает `http://127.0.0.1:8765/wizard?file=<путь к tasks.wizard.yaml>`.
2. Видит по карточке на задачу: title, spec_ref, scope_paths, acceptance,
   капы (max_tokens / max_cost_usd), гейт. Плюс lint-предупреждения
   (`forge lint` — советчик) и прогноз «не больше ~$X (сумма капов)».
3. Правит поля, жмёт «Сохранить черновик». Сервер валидирует контракт
   tasks.yaml (DAG, kebab-id, scope) **до** записи; при ошибке файл не
   изменяется, при успехе — атомарная замена (temp + `os.replace`).
   `depends_on` в форме не редактируется и сохраняется из исходного файла.
4. Запускает прогон из терминала — форма сама показывает команду
   `forge run --tasks <файл> --target .`.

### 1.3. Новичок смотрит «что вообще происходит»

Контекст: человек открыл UI без погружения в токены и состояния.

1. Если прогонов нет — пустое состояние с подсказкой: «Прогонов пока нет —
   запустите `forge run`».
2. Колонки подписаны по-русски («Очередь», «В работе», «Валидация», «Ревью»,
   «Заблокировано», «Провалено», «Готово»), цветовая кодировка состояний.
3. Отчёт простым языком (`forge report --plain`: «Сделано N из M», ✅/❌/⏸,
   «что дальше») существует **только в CLI** — в UI его нет (см. §3).

## 2. Каталог возможностей

### 2.1. Экраны и ручки API

| Экран / ручка | Данные | Действия | Ограничения |
|---|---|---|---|
| `GET /` (`/index.html`) — канбан | Статика `forge/ui_static/index.html` (встроенные CSS/JS, без внешних ресурсов). Данные подтягиваются JS через API. | Переключение прогона, вид «Канбан»/«Отчёт», открытие панели событий. Автообновление каждые 3 с. | Только чтение. Весь рендер — на клиенте. |
| `GET /api/runs` | Список прогонов из `runs/`: `run_id`, `started_at`, `package`, `provider`, `mock`, счётчики состояний `states{}`, `total_cost_usd` (сумма `cost_usd` по events.jsonl). | Выбор прогона в селекте. | Битый/отсутствующий `run.json` → пустые поля, сервер не падает. Каталоги без `run.json` тоже попадают в список. |
| `GET /api/run/<run_id>` | Мета прогона (`run.json` целиком), массив задач: `id`, `title` и `gate` (из tasks.yaml по `meta.tasks_path`), `state`, `cost_usd`, `tokens_in/out`, `repairs`, `note` (≤500 симв.). Итоги `totals` (суммы). | Рендер канбана и отчёта. | 404 при несуществующем/невалидном `run_id`. Только задачи **с journal-записями** (`tasks/<id>.json`); queued-задачи из очереди без записей не включаются (в отличие от CLI status). Снапшоты `*.history.json` (AF-12) исключены. |
| `GET /api/run/<run_id>/events?task=<id>&tail=<n>` | Последние `tail` событий `events.jsonl` (по умолчанию 50, максимум 500), опционально отфильтрованные по `task_id`. Поля события: `ts`, `phase`, `role`, `model`, `command`, `exit_code`, `tokens_in/out`, `cost_usd`, `note` (≤500 симв. + «…»). | Панель событий задачи (аналог `forge log`). | 404 при невалидном `run_id`. Битые строки JSONL пропускаются. Фильтр только по одной задаче; «все события прогона» UI не запрашивает. |
| `GET /wizard?file=<путь.yaml>` | HTML-форма черновика: карточки задач (title, spec_ref, scope_paths, acceptance, max_tokens, max_cost_usd, gate), lint-предупреждения, прогноз стоимости (сумма капов), подсказка команды запуска. | Просмотр/правка полей черновика. | `file` — существующий `*.yaml`/`*.yml`, иначе 400. Нельзя добавить/удалить задачу, изменить `depends_on` и порядок. |
| `POST /wizard/save` | Перезапись черновика из формы. | Сохранение с валидацией контракта до записи; атомарная замена; ответ — та же форма с сообщением «ok»/«err». | **Единственная мутация UI.** `runs/` не затрагивается. `depends_on` сохраняется из исходного файла. При провале контракта файл не меняется. |
| Прочие пути | JSON `{"error": "not found"}` | — | 404. |

### 2.2. Клиентская логика (index.html)

- **Колонки канбана** — фиксированный порядок `STATE_ORDER`; состояния вне
  списка (наследие старых прогонов) добавляются extra-колонками в конец.
- **Селект прогона**: по ум `/api/runs` — последний по имени; при обновлении
  выбор сохраняется, если прогон ещё существует.
- **Панель событий**: фиксированная справа (46% ширины, min 420 px),
  автопрокрутка вниз, закрытие по «✕» или смене прогона; обновляется вместе
  с деталями прогона.
- **Экранирование**: весь пользовательский контент проходит через `esc()`
  (XSS-защита на клиенте) и `html.escape` (wizard на сервере).
- **Заголовок шапки**: `provider · mock · started_at`, итог `$X.XXXX`.

### 2.3. Паритет с CLI (status / log / report)

| Данные | CLI | UI |
|---|---|---|
| Таблица задач прогона | `forge status` — **вся очередь** из tasks.yaml (топологический порядок), задачи без journal-записей показаны как `queued` → честный «N из M» | Канбан/отчёт — только задачи с journal-записями |
| Подсказка ожидания гейта | `forge status`: «⏸ Прогон ждёт решения: `forge accept <id> && forge resume <run>`» (`report._gate_wait`) | Нет |
| Метка гейта на задаче | В таблице status нет | Есть: `⛳ <gate>` на карточке |
| Журнал задачи | `forge log <task_id>` (note до 400 симв.) | Панель событий (note до 500 симв.) |
| Сводка | `forge report`: + per-run кап с вердиктом OK/ПРЕВЫШЕНИЕ, модели по ролям, версия промптов | Вкладка «Отчёт»: только таблица + итоги |
| Отчёт простым языком | `forge report --plain` («Сделано N из M», ✅/❌/⏸, следующие команды) | Нет |

## 3. Пробелы UX (констатация, без дизайна)

Что CLI умеет, а UI — нет:

1. **Гейт №3 из браузера**: `forge accept <task_id>` и `forge resume <run_id>`
   доступны только в терминале. UI не показывает даже подсказку «⏸ Прогон ждёт
   решения…» — владелец, смотрящий только в браузер, не узнает, что прогон
   стоит на гейте (задача выглядит обычной `done` с меткой `⛳`).
2. **Запуск прогона**: `forge run` / `forge resume` из UI недоступны; кнопки
   «запустить очередь» нет даже в wizard-форме (только текстовая подсказка
   команды).
3. **Просмотр diff ветки задачи**: ни изменённых файлов, ни `git diff` ветки
   задачи в UI нет; только note и события.
4. **Стоимость по времени**: нет графика/таймлайна стоимости и токенов —
   только агрегаты (на задачу и итого).
5. **Честный «N из M»**: UI не показывает queued-задачи без journal-записей,
   поэтому полная очередь и прогресс «N из M» видны только в `forge status` /
   `forge report --plain`.
6. **Отчёт простым языком** (`report --plain`): разделы «Получилось / Не
   получилось / Ждёт решения / Что дальше» — только CLI.
7. **Per-run кап и воспроизводимость**: вердикт по капу, модели по ролям,
   версия промптов (`forge report`) в UI-отчёте отсутствуют.
8. **Dry-run прогноз** (`forge run --dry-run`) в UI нет; wizard показывает
   лишь сумму капов.
9. **События всего прогона**: API умеет отдавать события без фильтра по задаче,
   но UI такой вид не использует; поиска по логам нет.
10. **Wizard-форма**: нельзя добавить/удалить задачу, менять `depends_on` и
    порядок задач — только правка полей существующих.
11. **Уведомления**: нет звука/бейджа при смене состояния или остановке на
    гейте; только пассивное автообновление.
12. **Язык интерфейса**: только русский (англ. версии UI нет).
13. **Список прогонов**: только выпадающий селект; таблицы прогонов со
    сравнением (стоимость, состояния) нет, хотя `/api/runs` эти данные отдаёт.
14. **Мобильная вёрстка**: панель событий min 420 px и колонки min 220 px на
    узком экране требуют горизонтальной прокрутки.

## 4. Нефункциональные требования

1. **Read-only к `runs/`**: сервер ничего не создаёт, не изменяет и не удаляет
   в `runs/`. Единственная мутация — перезапись одного YAML-файла черновика
   через `/wizard/save` (атомарно: temp-файл рядом + валидация контракта +
   `os.replace`; при ошибке исходный файл не тронут).
2. **Без ключей**: UI не вызывает LLM и не требует API-ключа; конфиг
   провайдера не загружается. Секреты в events.jsonl не попадают по контракту
   журнала (`journal.event`).
3. **Localhost**: биндинг только на `127.0.0.1`; порт по умолчанию 8765,
   `--port 0` — эфемерный (тесты). Аутентификации нет — предполагается
   локальный инструмент владельца.
4. **Офлайн-статика**: единственный `index.html` со встроенными CSS/JS; ноль
   внешних CDN, шрифтов, аналитики. Сервер — чистый stdlib (`http.server`,
   `json`, `urllib`, `html`, `tempfile`); из внешних зависимостей только
   PyYAML (уже в проекте). Статика читается из `forge/ui_static/` рядом с
   модулем — работает и в editable-install.
5. **Устойчивость к данным**: битый/отсутствующий `run.json`, `tasks/*.json`,
   строки `events.jsonl` не роняют сервер (пустые структуры / пропуск строк).
   `BrokenPipeError`/`ConnectionResetError` при ответе игнорируются.
   Защита от path traversal: `run_id` с `/`, `\`, `..` отклоняется (404).
6. **Кэш**: все ответы с `Cache-Control: no-store`; клиентский fetch тоже
   `no-store` — UI всегда показывает актуальное состояние runs/.
7. **Языки**: интерфейс — русский; документация (этот файл и `UI_SPEC.md`) —
   рус + англ.
8. **Обрезка данных**: `note` — 500 символов в API (карточки и события);
   `tail` событий — от 1 до 500; команда в лог-вьюере — до 200 символов в
   строке.
