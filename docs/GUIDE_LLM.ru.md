# Как LLM пишут код: теория, инструменты и место agent-forge

> Живой документ. Обновляется по мере развития agent-forge и конкурентов.
> Последняя ревизия: 2026-08. Если вы читаете это спустя месяцы — проверьте
> раздел «Альтернативы» на актуальность и поправьте своим PR.
> English version: [GUIDE_LLM.md](GUIDE_LLM.md).

Документ для новичка, который выбирает, **как** строить работу с LLM в своём
проекте, и решает, подходит ли ему agent-forge. Без маркетинга: где наше
решение сильно, где слабо и когда честнее взять другой инструмент.

## 1. Фундамент: чем LLM-ассистент отличается от компилятора

LLM не «знает» ваш проект. Всё, что модель учитывает при генерации, — это
**контекстное окно**: текст, который вы ей подали в этом конкретном запросе.
Из этого факта следуют все инженерные проблемы LLM-кодогенерации:

1. **Контекст = деньги и качество одновременно.** Каждый токен в окне стоит
   денег; при этом на длинных контекстах внимание модели деградирует —
   инструкция «не дублируй X» на 90-м килотокене заметно хуже, чем на 5-м.
   Значит, центральная задача любого инструмента — **отбор контекста**:
   дать модели ровно те файлы, контракты и решения, которые нужны для задачи.
2. **Модель не умеет проверять себя.** Она генерирует правдоподобный код,
   а не верный. Единственный надёжный валидатор — внешний: компилятор,
   тесты, линтер. Поэтому зрелые инструменты строятся вокруг
   **acceptance-команд**, а не вокруг «умного промпта».
3. **Без явных границ агент разрастается.** Дайте модели «доработай сервис»
   без границ — получите правки в восьми файлах, рефакторинг по вкусу модели
   и дубль существующей модели данных. Отсюда — **scope-контроль** и
   **каталог существующих сущностей** как обязательные механизмы.
4. **Воспроизводимость не возникает сама.** Если результат зависит от того,
   какие файлы модель решила прочитать сегодня, — повторить прогон нельзя.
   Нужны журналирование и детерминированные части пайплайна.

## 2. Спектр решений 2026 года

Инструменты отличаются в первую очередь тем, **кто и как отбирает контекст**
и **где стоят точки контроля человека**.

### 2.1. Чат в браузере (ChatGPT, Claude, DeepSeek-web)

Контекст копирует человек руками. Полный контроль, ноль автоматизации.
Подходит для одноразовых вопросов; для разработки проекта — нет: человек
становится узким местом и источником ошибок отбора.

### 2.2. IDE-копилоты (GitHub Copilot, Cursor, Windsurf)

Контекст отбирает IDE: автодополнение + чат по индексу кодовой базы
(эмбеддинги/RAG + эвристики). Сильны в «пишу и подсказывает», слабее в
многошаговых задачах; RAG-индекс недетерминирован — семантическая близость
не равна связи по контракту. Гейт между «предложено» и «закоммичено» — вы
сами, в реальном времени. Хороший выбор для интерактивного pairing'а;
слабый — для аудируемых, воспроизводимых прогонов.

### 2.3. Агентные CLI (Claude Code, Aider, goose, OpenHands, Codex CLI)

Модель работает в цикле «модель ↔ инструменты» прямо в репозитории:
читает файлы, правит, гоняет тесты. Контекст-стратегии:
- **Aider** — repo-map на tree-sitter: сигнатуры всего репо компактно,
  файлы целиком — только редактируемые. Детерминированно и дёшево;
- **Claude Code** — следование по импортам + поиск, иерархические
  CLAUDE.md/AGENTS.md как слой конвенций;
- **OpenHands / swe-agent** — автономные агенты для бенчмарковых задач,
  контроль минимален.

Это самый живой класс инструментов. Общая слабость: управление бюджетом,
гейты и аудит — чаще опциональны, чем встроены; состояние прогона обычно
живёт в сессии, а не в журнале на диске.

### 2.4. Спек-ориентированные методологии (GitHub spec-kit, BMAD-метод)

Пайплайн «спецификация → план → задачи → код» поверх агентных CLI.
Сильная идея: спека — источник истины, код — производная. Слабость:
это библиотеки промптов и процедур поверх чужого раннера; исполнение,
бюджеты и валидация остаются на нижележащем инструменте.

### 2.5. Оркестраторы прогонов с гейтами (agent-forge — здесь)

Фокус не «умный агент», а **управляемый конвейер**: очередь задач как
контракт (tasks.yaml), у каждой задачи — scope, acceptance-команды
владельца, бюджет, гейт; состояние — на диске, каждый вызов модели — в
журнале; прогон можно убить и возобновить. Модель — сменная деталь
(OpenAI-совместимый endpoint), интеллект — в структуре процесса.

## 3. Ключевые tradeoff'ы (чем жертвует каждый подход)

| Ось | Копилоты (2.2) | Агентные CLI (2.3) | Спек-методологии (2.4) | agent-forge (2.5) |
|---|---|---|---|---|
| Скорость старта | мгновенно | минуты | часы на методологию | минуты (wizard) |
| Интерактивность | полная | высокая | средняя | низкая (гейты) |
| Контроль бюджета | нет | слабый | нет | капы на задачу/прогон/день |
| Валидация результата | глазами | тесты по усмотрению модели | по процедуре | acceptance-команды владельца, заморожены |
| Аудит/воспроизводимость | нет | сессия | зависит от раннера | полный журнал events.jsonl |
| Отбор контекста | RAG (недетерм.) | repo-map/поиск | вручную по спеке | карта сущностей + граф импортов |
| Порог входа | нулевой | низкий | высокий | средний |

## 4. Как agent-forge отбирает контекст (наш ответ на §1)

Детерминированно, без эмбеддингов (обоснование выбора — в этом разделе
сравнение с RAG: недетерминизм ломает воспроизводимость прогонов):

1. **`forge map`** — AST-скан проекта → `canon/entities.json`: все публичные
   сущности (модели, контракты, сервисы) с сигнатурами и графом импортов.
2. При сборке промпта задачи coder получает три слоя:
   - файлы своего **scope** — читает и правит сам (write_file ограничен scope);
   - **каталог имён всех сущностей** проекта — анти-дубль: «`UserModel` уже
     есть в `models/user.py`, импортируй, не пиши заново»;
   - **сигнатуры соседей** по графу импортов (глубина 1) — связанные
     контракты видны без чтения их файлов целиком.
3. `AGENTS.md` целевого репо — слой конвенций в том же промпте.
4. Спека и canon — выдержками с жёстким лимитом (30K символов).

## 5. Когда agent-forge — правильный выбор, а когда нет

**Берите agent-forge, если:** нужен аудируемый прогон с бюджетом и гейтами;
работа ведётся пакетами задач от спецификации; проект большой/легаси и важен
контроль scope; вы хотите сменные дешёвые модели вместо премиум-подписки.

**Честно берите другое, если:** нужен интерактивный pairing в редакторе
(Copilot/Cursor); задача разовая и маленькая (чат); вы исследуете границы
автономных агентов (OpenHands); у вас нет никаких проверок и вы не готовы
их написать — acceptance-ориентированность тогда обернётся трением.
