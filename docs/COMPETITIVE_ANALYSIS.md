# agent-forge — конкурентный анализ и аудит

Дата: 2026-08-20 · Объект: `github.com/Xarawg/agent-forge` (ветка `master`) · Демо: https://xarawg.github.io/agent-forge/

---

## 1. Что это за инструмент (коротко)

`agent-forge` — локальный оркестратор **серийной** LLM-кодогенерации: очередь задач из `tasks.yaml` (DAG, scope, acceptance-команды, бюджеты), цикл «coder → acceptance-тесты → reviewer (вторая модель) → repair (≤3)», человеческие гейты (`forge accept`), жёсткие капы бюджета в USD (per-task / per-run / per-day), полный журнал `runs/<run_id>/events.jsonl`, resume со снапшотов истории, mock-режим без API-ключа, read-only kanban UI. Любой OpenAI-совместимый провайдер через YAML-пресеты (DeepSeek, OpenRouter free, Ollama). Git: ветка на задачу, локальные коммиты, push никогда.

**Ниша:** не «pair-programmer» (aider) и не «автономный сотрудник в облаке» (Devin), а **governable batch-очередь**: запустить 10–30 специфицированных задач подряд с гарантиями по деньгам, тестам и аудиту.

## 2. Покрывает ли инструмент то, что обещает

Проверено по коду, а не по README. Вывод: **обещания в основном подтверждаются**, но есть разрывы в инфраструктуре вокруг кода.

| Обещание (SPEC/README) | Статус | Доказательство |
|---|---|---|
| Test gates (acceptance-команды до done) | ✅ | `runner.py::_validate`, exit_code != 0 → repair |
| Reviewer второй моделью + repair ≤3 | ✅ | `runner.py::_run_task`, цикл `max_repairs + 1` |
| Бюджетные капы per-task/run/day → `blocked` | ✅ | `_check_budgets`, `_day_cost` по всем `runs/*/events.jsonl` |
| DISPUTE/STUCK вместо галлюцинаций | ✅ | `agents.py::parse_verdict`, маркеры → `blocked`/`failed` |
| Scope-контроль записи, `canon/` read-only | ✅ | `tools.py::check_write_allowed`, тесты `test_scope.py` |
| Блокировка `npm install` / `pip install` в коде | ✅ | `DENY_COMMAND_PATTERNS`, тесты `test_tools_policy.py` |
| Resume после kill (снапшоты истории) | ✅ | `_history_path` + `test_resume_history.py` |
| Human gate `forge accept` + локальный merge | ✅ | `runner.py::accept`, `_pending_gate` |
| Никогда не push | ✅ | в коде нет `git push` |
| Mock-режим `FORGE_MOCK=1` | ✅ | `test_mock_run.py`, весь CI без ключа |
| Провайдер-пресеты + retry/backoff + fallback-модели | ✅ | `llm.py::_chat_with_fallback`, экспоненциальный backoff |
| Planner: `forge import` из SPEC.md | ✅ | `cli.py::cmd_import` + `prompts/10_planner.md` |
| Тесты одной командой | ✅ | **36 passed** локально (pytest, mock) |
| `mypy --strict` | ✅ | clean, 13 файлов |
| `ruff check` | ❌ | 1 ошибка: `docs/fix_links.py` — unused import `re` |
| CI GitHub Actions | ❌ **мёртвый** | workflow триггерится на push в `main`, но вся работа идёт в `master`; `origin/main` — это «Initial commit». CI на реальных коммитах **никогда не запускался**. А когда запустится — упадёт на ruff-ошибке выше |

### Замечания к качеству реализации (не баги, а слабые места)

1. **Reviewer видит не diff, а дамп содержимого** — `_written_snapshot` читает файлы целиком и обрезает на 3000 символов каждый. На больших задачах reviewer ревьюит усечённый контент. Осознанное v1-решение (зафиксировано в DECISIONS), но это главное место потери качества контроля.
2. **`run_command` — дыра в «guardrails» по сути**: allowlist разрешает `python`, `node`, `npm test` — через `python -c "..."` или скрипт в `package.json` агент выполнит произвольный код. Scope-контроль реален только для `write_file`. Для локального инструмента доверенного владельца это приемлемо, но формулировка «agents can only write where you allow» на сайте сильнее фактики.
3. **Контекст без карты репозитория**: coder получает spec-excerpt (30K символов) + `list_dir`/`read_file`. Нет repo-map (tree-sitter), нет retrieval — агент сжигает шаги на обнаружение структуры. Это прямая причина более высокого расхода токенов vs aider.
4. **Acceptance-команды — доверенный shell** (`shell=True`, строки из tasks.yaml). Документировано, но стоит явно писать в threat-модели.
5. **`docs/fix_links.py` лежит в деплоимом каталоге** `./docs` и улетает в GitHub Pages-артефакт; заодно он же ломает ruff.
6. Дублирование `site/index.html` и `docs/index.html` (отличаются только CRLF/LF) — два источника правды, неизбежный дрейф.

**Вердикт раздела: ядро честное — заявленный пайплайн реализован и покрыт тестами; врут не фичи, а инфраструктура (CI мёртв) и одна маркетинговая формулировка про scope.**

## 3. Демо-сайт и GitHub Pages

**Статус деплоя:** сайт жив и раздаётся по `https://xarawg.github.io/agent-forge/` из `./docs` через `actions/deploy-pages@v4` — деплой настроен правильно и работает.

### Что хорошо

- Дизайн не «дефолтный AI-лендинг»: тёмная тема с красным акцентом, film-grain оверлей, плавающая pill-навигация, flush-left hero, моноширинные акценты — выглядит взросло.
- **Интерактивное демо пайплайна** (Next Step / Auto Play, сценарии Happy Path и Repair Loop) — правильная идея для объяснения продукта.
- Двуязычность EN/RU с переключателем, контент (use cases, quick start, «Why») полный и конкретный, без пустых эпитетов.
- Один самодостаточный HTML-файл, без сборки — уместно для Pages.

### Что плохо / риски

1. **«Live Demo» — это scripted-симуляция** на JS, не реплей реального прогона. На странице это никак не помечено. Для инструмента, чей главный аргумент — «мы не галлюцинируем и всё логируем», несолидно: либо подписать «simulation», либо (лучше) воспроизводить реальный `events.jsonl` из mock-прогона.
2. **Ссылки на доки** (`SPEC.md`, `ARCHITECTURE.md`…) ведут на сырые markdown-файлы в Pages-артефакте — откроется plain text / 404-стиль. Должны вести на `github.com/Xarawg/agent-forge/blob/master/docs/...`.
3. **Внутренние id референсов дизайна утекли в продакшн-CSS** (`/* from qtAq3fyt */`, `lSZo3qgS`, `DRkP7PQd`, «synthesized from musepool refs»). Служебные метки не должны жить в закоммиченном коде.
4. Нет OG/Twitter-card meta, нет favicon, нет скриншота реального UI (`forge ui`) — а это самый убедительный визуальный аргумент продукта.
5. Канбан-скриншот/секция про `forge ui` на сайте отсутствует вовсе.

**Вердикт раздела: деплой — работает; сайт — выше среднего для OSS-лендинга, но подрывает собственный messaging (фейковое демо, битые ссылки на доки, служебный мусор в CSS).**

## 4. Конкурентный ландшафт

Прямых аналогов «batch-очередь спек-задач с USD-капами» нет — но покупатель сравнивает с общим рынком coding-агентов:

| Конкурент | Тип | Звёзды (≈, 2026) | Отношение к agent-forge |
|---|---|---|---|
| **aider** | terminal pair-programmer | ~46k | Пересечение: git-коммиты, любые модели, Ollama. Сильнее: repo-map (tree-sitter), зрелость, сообщество |
| **OpenHands** | автономный агент в Docker-сандбоксе | ~76k, SWE-bench 72.8% | Сильнее почти везде: сандбокс, параллельные агенты, browser, SDK, облако. Слабее: нет человеческих гейтов между задачами и per-day бюджетов |
| **Plandex** | plan-driven, diff-sandbox, ветвление планов | ~15k | Ближайший по философии «план → задачи». Сильнее: diff-review сандбокс, rewind/branching, контекст до 2M токенов. **Важно: облако сворачивается, проект теряет темп — окно возможностей** |
| **Claude Code / Codex CLI / Gemini CLI / Goose** | терминальные агенты вендоров | — | Сильнее: нулевой сетап, MCP, сабагенты, подписка вместо токенов. Не конкурент по батч-оркестрации, но забирают внимание |
| **Kiro (AWS)** | spec-driven IDE | — | **Идейно ближайший**: spec → requirements → tasks → исполнение с hooks. Подтверждает рынок «spec-driven», но это IDE, не batch-оркестратор |
| **Devin / Jules / Copilot coding agent / Sweep** | облачные issue→PR | — | Другой класс (облако, push, PR). Не конкуренты по local-first, но задают планку UX |
| **SWE-agent / mini-swe-agent** | research/benchmark | — | Планка воспроизводимости и оценки качества |

### Что есть у конкурентов и нет у agent-forge

1. **Сандбоксинг исполнения** (OpenHands: Docker-контейнеры) — у вас команды бегут на хосте.
2. **Repo-map / умный контекст** (aider tree-sitter, Plandex до 2M токенов) — у вас сырой excerpt + ручной list_dir.
3. **Настоящий diff-review** (Plandex sandbox, aider atomic commits) — у вас дамп файлов с обрезкой 3000 символов.
4. **Параллелизм** (OpenHands — сотни агентов; Claude Code — сабагенты) — у вас serial by design (v1).
5. **Rewind / checkpoints / ветвление планов** (Plandex) — у вас только resume.
6. **MCP / интеграции** (GitHub, Jira, Slack, Sentry) — отсутствуют.
7. **Бенчмарк-цифры** (SWE-bench у OpenHands/SWE-agent) — у вас нет никакой измеренной доказательной базы.
8. **Упаковка и дистрибуция**: нет на PyPI, нет релизов, нет бейджей; установка только `pip install -e .` из клона.
9. **Сообщество**: у лидеров десятки тысяч звёзд, Discord, контрибьюторы.

### Что есть у agent-forge, чего нет (или редкость) у конкурентов

1. **Per-day бюджетный кап в USD по всем прогонам** — уникально. Per-task лимиты есть у OpenHands, но «не больше $X в день на всё хозяйство» — нет ни у кого.
2. **Человеческие гейты между milestone'ами** в серийном батче (`forge accept` → пауза очереди) — у автономных инструментов человек только в начале или в конце.
3. **Маркеры DISPUTE/STUCK как первоклассный исход** — «остановись видимо, не выдумывай». В таком явном виде ни у кого.
4. **Mock-режим полного цикла без API-ключа** — killer-фича для CI и онбординга; у конкурентов тесты требуют ключи или мок-фреймворки.
5. **Бесплатные провайдеры из коробки** (OpenRouter `*:free` пресет + per-day кап = реально $0-эксплуатация).
6. **Нулевая зависимость от вендора и облака**: stdlib-UI, локальный git, никаких аккаунтов. Windows-first — редкость (у большинства Windows — второй сорт).
7. **Читаемость кодовой базы**: ~2100 строк, strict-mypy, журнал — plain JSONL. Для аудита/форка — лучшее на рынке соотношение «возможности / строки кода».

### Что сделано хуже, чем у конкурентов (из того, что есть у обоих)

- **Контекст-инжиниринг** хуже aider/Plandex (нет repo-map) → больше токенов и шагов на задачу.
- **Review-качество** хуже Plandex (усечённый дамп vs diff-сандбокс).
- **UI** — read-only kanban без стриминга vs живые TUI/веб-интерфейсы OpenHands/Cline.
- **Git-интеграция** — только локальные ветки/коммиты; нет опционального PR-драфта (Devin/Sweep/Copilot задают ожидание «issue → PR»).
- **Доказательность**: нет бенчмарка, нет публичной галереи реальных прогонов — вся убедительность держится на README и демо-симуляции.

## 5. Перспективы развития

**Рыночное окно реально.** Plandex (ближайший по духу) сворачивает облако и теряет темп; aider замедлился (последний релиз v0.86.0, август 2025); вендорские CLI не решают batch-governance; Kiro доказал спрос на spec-driven. Ниша «**управляемая серийная кодогенерация с финансовыми гарантиями, local-first**» свободна. Она узкая, но защищаемая — и хорошо монетизируется в enterprise-сегменте (аудит, бюджеты, on-prem).

### Рекомендованная дорожная карта (приоритеты)

**P0 — честность и гигиена (дни):**
1. Починить CI: триггер на `master` (или мердж в `main`), исправить ruff-ошибку.
2. Пометить демо как simulation или воспроизводить реальный mock-`events.jsonl`; починить ссылки на доки; убрать служебные id из CSS; убрать `fix_links.py` из `./docs`; оставить один источник сайта.
3. Переформулировать scope-claim: граница реальна для `write_file`, не для `run_command`.

**P1 — доказательная база (недели):**
4. Публичный мини-бенчмарк: 10–20 эталонных задач, таблица «модель × стоимость × % done» — ваша дисциплина журналирования делает это почти бесплатным. Это ответ на SWE-bench-цифры OpenHands.
5. Галерея реальных прогонов (экспорт `runs/` в статические страницы) — и на сайт вместо симуляции.
6. PyPI-пакет + GitHub Releases + бейджи.

**P2 — продуктовая глубина (месяцы):**
7. Настоящий git-diff для reviewer (ветка vs base) вместо дампа файлов — самое дешёвое повышение качества контроля.
8. Repo-map (aider-style, tree-sitter или хотя бы ctags/заголовки файлов) в контекст coder'а — главный рычаг снижения стоимости задачи.
9. Опциональный Docker-сандбокс для `run_command` (закрывает главный security-gap).
10. Параллелизм независимых ветвей DAG (v2, уже отмечено в SPEC §7).
11. Опциональный draft-PR (за явным флагом, default off — не ломая NFR-5).

**P3 — экосистема:** MCP-сервер (agent-forge как инструмент для Claude Code/Cline), экспорт отчётов, шаблоны пакетов (port-to-TS, test-gen, docs-sync — они уже есть на сайте как use cases).

### Главные риски

- **Рынок сжимается сверху**: вендоры (Claude Code, Codex) добавляют batch/queue-фичи и подписочные лимиты, которые «достаточно хороши».
- **Solo-maintainer risk** — тот же, за что критикуют aider; нужен CONTRIBUTING + второй мейнтейнер раньше, чем traction.
- **Узкая ниша** может оказаться слишком узкой для adoption без кейсов «мы прогнали N задач за $X» — отсюда приоритет P1.

## 6. Итог одной строкой

Ядро продукта честное, компактное и занимает реально свободную нишу (governed batch codegen с USD-капами и human gates); срочно требуется гигиена (мёртвый CI, демо-симуляция, битые ссылки), затем доказательная база (бенчмарк + реальные прогоны) и два инжиниринговых шага (git-diff для reviewer, repo-map для coder'а) — это превращает «аккуратный личный инструмент» в защищаемый OSS-продукт.
